# 审查 AlonaBot

本技能用于只读审查和交付前自审。跨模块大改动使用独立审阅者，可用时同时加载 `code-review-expert`；不可用时按以下项目检查，不能只凭测试通过给出认可。

## 固定对象

检查 `git status -sb`、范围 diff 与 stat，记录 base 和 head 的完整 SHA。PR 没有工作区 diff 不表示分支没有改动。读取原始需求或 Issue、[架构地图](../../../ARCHITECTURE.md)和[编码规范](../../../docs/coding-standards.zh-CN.md)。未获修复授权时不改源文件。

## 分开审查两条轴

**Spec**：追踪输入到输出、提交与副作用；检查身份、代次、注册与就绪门、调用预算、取消因果、有效部分结果、进程树、锁与恢复。以需求和现行行为判断缺陷，不把需求没有承诺的能力当作遗漏。

**Standards**：以 Google Go Style Guide（可用时加载 `go-google-style-*` 技能）和[编码规范](../../../docs/coding-standards.zh-CN.md)为准，检查语义所有者、允许的 import 边、接口是否减少调用者负担、类型与常量是否就近、错误链和资源生命周期。按[注释技能](../alonabot-code-commenting/SKILL.md)逐文件核查包文档、命名术语、文档注释与 step 注释，检查防御性的多余检查、首次发布前的兼容层（追加的状态库迁移、零值沿用旧语义、旧名别名），以及提交的测试是否只有集成测试、是否违反 `sdk/` 与 `internal/core/supervisor/` 的限制。判断性建议不能冒充硬规则。

核对生成源、调用者、fixture 和文档是否同步。已有检查可覆盖的内容不重复索要测试；跨平台或外部环境缺失要明确写出，不能用 fixture 顶替。

用 `git diff --numstat <base>...<head> -- '*_test.go' '*/testdata/*'` 与产品代码的新增行对比测试增量；测试增量超过产品增量时，要求说明为什么不能移到本地测试。

## 输出可执行结论

每项问题给出文件与行号、触发条件、用户影响和最小修复。严重度按影响给出：P0 立即阻断，P1 合并前修复，P2 一般缺陷或维护风险，P3 可选建议。只列可证实的问题；「文件太长」「应该有接口」本身不是缺陷。

两条轴分别报告，最后说明是否建议合并、关键证据和真实缺口。审查请求不等于写入授权；获准修复后回到开发与测试流程。在 GitHub 上提交意见时，同一账号不能对自己的 PR request changes，改用 PR 评论。
