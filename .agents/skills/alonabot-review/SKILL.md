# 审查 AlonaBot

本技能用于只读审查和交付前自审；跨模块大改动使用独立审阅者，可用时同时加载 `code-review-expert`。不可用时照以下项目检查，不能仅凭测试通过给出认可。

## 固定对象

检查 `git status -sb`、范围 diff/stat，记录 base/head SHA。PR 没有工作区 diff 不表示分支没有改动。读取原始需求、对应 [PLAN](../../../spec/PLAN.md) 所指章节实施计划中的工作包、[架构地图](../../../ARCHITECTURE.md) 和 [编码规范](../../../docs/coding-standards.md)。未获修复授权时不改源文件。

## 分开审查两条轴

**Spec：**追踪输入到输出、提交与副作用；检查身份、代次、注册/就绪门、调用预算、取消因果、有效部分结果、进程树、锁与恢复。以当前工作包的停止条件判断缺陷，不把后续批次未承诺的能力当作本批次遗漏。

**Standards：**以 Google Go Style Guide（可用时加载 `go-google-style-*` 技能）和 [编码规范](../../../docs/coding-standards.md) 为准，检查语义所有者、允许的 import 边、接口是否减少调用者负担、类型/常量是否就近、错误链和资源生命周期。按 [编码规范](../../../docs/coding-standards.md) 和 [注释技能](../alonabot-code-commenting/SKILL.md) 逐文件核查包文档、命名术语、文档注释、step 注释、防御性的多余检查、首次发布前的兼容层（追加的状态库迁移、零值沿用旧语义、旧名别名），以及提交的测试是否只有集成测试、是否超出 goal 语句列出的范围、有没有违反 `sdk/` 与 `internal/core/supervisor/` 的限制（D-86）；判断性建议不能冒充硬规则。

核对生成源、调用者、fixture、文档和 [验收证据](../../../spec/TEST-MATRIX.md)。已有检查可覆盖的内容不重复索要测试；跨平台或外部环境缺失要明确，不能用 fixture 顶替。

## 审查执行者的切片 PR

审查者在合并前按以下顺序检查；合并授权和合并条件见 [贡献流程「角色与合并」](../../../CONTRIBUTING.md#角色与合并)。

1. 记录 PR 的 base/head 完整 SHA，读取当前 head 的检查结果。读 docs/goals/ 中该 goal 的语句和 PR 正文：核对 PR 没有偏离语句，每个 task 的证据与 commit 对得上。切片卡 `goal-N/` 被 git 忽略，只留在执行者本地，需要时向执行者索取。
2. 读完整 diff，按上面两条轴审查。超出语句「范围」的修改、语句没要求的接口或功能、语句没列出的提交测试、注释里的阶段编号都算问题。用 `git diff --numstat <base>...<head> -- '*_test.go' '*/testdata/*'` 与产品代码的新增行对比测试增量，在审查结论中写明数字；测试增量超过产品增量时，逐个说明为什么不能移到本地。
3. 针对语句中的行为要点和 PLAN 该工作包的失败停止条件，自己写临时测试（`*_local_test.go` 或 `tmp/test/`）实际运行，试着让它在这些条件下出错。只读代码或只看 CI 通过，不能下结论。这些临时测试不交给执行者提交。
4. 有问题时用 `gh pr review --request-changes` 提出，每条意见对应一个 FIX，写明位置、触发条件、影响和期望的修复，由执行者修复。意见针对产品代码的缺陷，不要求执行者往提交的测试里补用例；回归放在本地，由执行者在回复中写明名字和结果。提交的测试本身错误或缺少语句列出的场景时，才要求修改它。审查者不替执行者改产品代码，只推送切片状态和证据记录。
5. 全部通过后，在 PR 分支上把所属章节实施计划切片表中的状态改为「已完成」，补上 PR 正文「文档同步」列出的内容，等 CI 在新 head 上通过，再按贡献流程合并，并确认 `main` 的 CI 结果。
6. 合并后，按实际代码修订 docs/goals/ 中依赖它的 goal（可能在其他章节）：补全接口段，去掉状态中已合并的前置。对照全部章节实施计划的「已完成」核对每个未完成 goal 的前置：前置都已完成的 goal 必须在同一个 goals PR 中按 main 的代码改写语句（接口、行为、测试段写到可直接派发）并改为「待派发」，总览行与状态行一起改，不留「前置均已合并、语句待改写」的中间状态。确实无法改写时（缺少未列为前置的切片、需要改契约），在状态中写明缺什么，并请维护者决定是否调整前置。

## 输出可执行结论

每项问题提供文件/行号、触发条件、用户影响和最小修复。严重度按影响给出：P0 立即阻断，P1 合并前修复，P2 一般缺陷或维护风险，P3 可选建议。只列可证实的问题；“文件太长”“应该有接口”本身不是缺陷。

两条轴分别报告；最后说明是否建议合并、关键证据和真实缺口。未被接受的契约重定义仍是未完成事项。后续用户授权修复后，回到开发与测试流程，不把审查请求自动当成写入授权。
