# Go 代码与注释规范

本文件负责文件组织、Go 编码和注释的审查规则；模块与依赖方向由 [架构地图](../ARCHITECTURE.md) 负责，行为由 [spec](../spec/README.md) 负责。新增或调整约定时同步相关仓库技能和 PR 检查项。

## 按职责分文件，而不是按语法分类

- 先确定语义所有者，再决定包与文件。类型、方法、校验及专属常量就近放置；小类型与方法放在一起，大类型可按入站、出站、存储等真实操作拆文件。
- DTO、值对象或协议载荷按完整主题集中，例如调用、注册、消息；结构体含 mutex、channel、连接或生命周期状态时，它属于实现，不是共享 DTO。
- 共享数据契约可以使用职责明确的声明文件；其中放类型和相关枚举，不放 I/O、业务编排或有副作用的初始化。构造、校验和序列化属于实际执行这些行为的所有者。
- 常量跟随其约束的机制。只有确实独立共享的一组协议定义才单独成文件；不建立跨领域的 `dto.go`、`types.go`、`constants.go` 或 `utils.go` 杂物箱，也不要求一个类型一个文件。
- 不以行数限制触发拆分。判断标准是修改一个操作需要跳转多少文件、状态是否仍有唯一所有者、调用者是否更容易正确使用。

例如，`Budget` 与预算方法可以放进 `budget.go`；`Request`/`Response` 可以构成同一调用契约；请求状态枚举留在请求状态机旁。生命周期按准备、激活、停止组织，无须把它们的配置与结果类型集中搬走。

## 保持 Go 接口和副作用清晰

- 使用 `go.mod` 指定的 Go 版本和 `gofmt`，保留 `ID`、`URL`、`HTTP` 等 initialism 的大小写，同一类型的 receiver 命名一致。
- 优先具体类型、标准库和已有实现；在真实消费边界定义小接口，不为每个实现、每个测试或未来需求创建接口。
- 适用取消的函数以 `context.Context` 为首参并向下传递。每个 goroutine、连接、锁、临时文件都要有明确所有者与结束路径。
- 用 `%w` 保留错误链；只在拥有处理权的层记录错误，不逐层重复打印。部分成功的有效结果与错误一起保留，不伪造空成功。
- `cmd/alonabot` 负责参数与依赖装配；协议、数据库和进程逻辑留在各自所有者。并发字段的锁、状态转换和资源释放顺序必须可审查。
- 新依赖先说明必要性与现有替代方案，取得维护者明确同意后才添加。限额、超时、重试、截断或降级必须有契约要求或可复现故障依据，保留完整错误与数据。

## 每个手写代码文件都有职责头注释

适用于产品源码、测试、示例、脚本、`.proto` 和工作流/配置文件。使用相应语言的注释语法，在文件顶部说明本文件做什么；边界不明显时再说明不负责什么。Markdown 文档用标题后的导语说明用途，技能保留必须位于首部的 YAML frontmatter。

保留许可证、shebang、Go build tag、cgo 和生成指令要求的位置、空行及作用域。Go 文件的职责注释放在 `package` 前；一个包只需一个合适的 `Package <name>` 包文档，其余文件说明自己的职责，不重复整份包说明。

生成文件保留生成器产生的头注释，不手工补写；需要更多说明时修改 `.proto`、模板或生成器。锁文件、二进制 fixture 等不支持自由注释的机器格式不强行插入文本，其用途在所有者文档中说明。

```go
// 本文件负责停止单个插件：冻结派发、排空调用并按停止预算回收进程树。
package host
```

## 每个类、结构体及字段都说明含义

无论公开还是私有，每个类和结构体都说明职责，每个字段都写字段注释，包括匿名嵌入字段。写清领域含义；涉及单位、零值、可选性、所有权、锁保护或生命周期时在对应字段补充。不同含义的字段分开声明，不靠一个泛泛的类型注释代替逐字段说明。

```go
// StopTiming 描述一次插件停用的阶段预算。
type StopTiming struct {
	// Drain 是冻结新调用后留给既有调用链完成的最长时间。
	Drain time.Duration
	// Total 是从停用开始到进程树必须终止的总预算。
	Total time.Duration
}
```

类或结构体字段的解释与声明放在一起；函数局部或匿名结构体同样适用。生成类型的字段说明写在其源 Schema 中。不要承诺实现并未提供的并发安全、原子性、回退或重试保证。

## 函数说明契约，多步骤流程写 step comment

每个具名函数和方法在声明前说明作用；公开 Go 声明以符号名开头，必要时写清副作用、取消、错误和提交结果。闭包的作用紧邻使用处说明；明显的单表达式适配不额外堆叠说明。

有多个明确逻辑阶段时，在每段逻辑前用 `// 1. ...`、`// 2. ...` 标出目的和顺序约束。编号层级保持一致，调整逻辑时同步顺序；注释紧贴真正执行的代码段，不在函数开头复制一份目录。

```go
// WriteFrame 编码并串行写出完整帧；编码失败时不修改底层流。
func (w *Writer) WriteFrame(env *pb.Envelope) error {
	// 1. 在取得写锁前完成编码与帧长度校验。
	frame, err := EncodeFrame(env)
	if err != nil {
		return err
	}

	// 2. 整帧写出期间独占写端，避免并发帧交错。
	w.mu.Lock()
	defer w.mu.Unlock()
	n, err := w.w.Write(frame)
	if err == nil && n != len(frame) {
		return io.ErrShortWrite
	}
	return err
}
```

一段完整逻辑一个注释，不给每个赋值、`if err != nil`、循环或 return 编号。只有单一操作的 getter、转发函数和短函数保留作用说明即可，不强凑步骤。阶段内只有存在独立不变量或不明显取舍时再加意图注释。

样式参考 [AstrBot exporter.py](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/backup/exporter.py) 的文件职责说明和导出阶段划分；本项目的逐字段说明、简体中文和 Go 注释语法以本文件为准。

## 如何应用和审查

新增手写文件完整遵守以上规则；修改已有文件时补齐文件头以及本次触及的类型、字段、函数和逻辑阶段。整库注释补齐是独立任务，不夹带在产品修复中；已知缺口不能被称为已满足规范。

`gofmt`、编译与生成一致性检查机械规则。职责划分、字段解释和 step comment 的准确性由人工或 agent 按 [注释技能](../.agents/skills/alonabot-code-commenting/SKILL.md) 审查；CI 通过不代表这些语义规则自动通过。普通注释修改只检查内容、格式和相关引用；涉及 `go:generate`、build tag 等可执行指令时验证实际消费者。
