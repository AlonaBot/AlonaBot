# 分层休眠与按需唤醒设计

**日期：** 2026-10-28

**基线：** main `c79d723`

**状态：** 方向已确认（D-53～D-58），实施工作包为 [PLAN §7 的 S-01～S-06](../PLAN.md#7-休眠扩展)。本文是待并入契约的设计依据：各 S 工作包实施前先把对应小节并入 CONTRACTS、WIRE、DESIGN，之后以契约为准，本文不再同步细节。

S 工作包不是 T-10 的前置，不进入 v0.1 发布门槛；v0.1 的行为与验收不因本文改变。

**修订（2026-11-14，D-153）：** 只做插件级休眠，Core 与全部 Adapter 始终常驻。§1 的第 3、4 条，§3.1 的 `scale_to_zero`，§5、§6 与 §7.2～§7.4 不再实施；S-04、S-05 已取消。注册了消息类事件路由或 Raw 路由的插件缺省常驻；空闲时长可以全局与按插件配置，管理员可以让插件永不休眠，见 §8。

## 1. 目标

根据实际使用情况自动释放闲置资源，同时保证消息、命令、HTTP 请求、跨插件调用和定时任务能按需唤醒对应组件。

1. **降低常驻内存。** 无需持续工作的 Native Go 插件可以完全退出进程。
2. **保持用户体验。** 插件休眠与唤醒由 Core 完成，用户不需要手动启动插件。
3. **Adapter 有条件休眠。** 只有在平台连接允许、入站消息存在可靠唤醒来源时才停止 Adapter 进程。
4. **Core 深度休眠。** 有外部消息入口与定时唤醒器时，整个实例可以停止或由平台挂起。
5. **任务可靠。** 定时任务的执行权、去重和恢复不依赖插件进程长期存活。
6. **控制复杂度。** 复用 Router、Supervisor、Scheduler、ActiveGeneration 和现有 IPC 生命周期。

不追求所有插件都能休眠，不引入通用进程快照，也不要求所有部署环境支持整机挂起。

## 2. 约束

已有决策继续有效：D-01（每插件包一个子进程）、D-19（调度归 Core）、D-25（插件 HTTP 走 Core 统一入口）、D-26（每个 Adapter 包一个进程，承载全部实例）、D-32（发行包与库模式并存）、D-46（OneBot 11 首发只用正向 WebSocket）。

已有可复用的部分：Native 插件的启动、握手、准备、激活与停止；`OnStart → REGISTER → OnReady → ACTIVATED`；`ActiveGeneration` 与逐插件管理锁；TCP/stdio 双 IPC 与有限自动重启（`internal/core/host` 的 `RestartPolicy`，5 分钟窗口内第 3 次异常退出停止重启）；`contracts/schedule` 的触发时间计算；WIRE 中已有 `ActivationReason` 的 `resume`。Router、Scheduler 执行、Adapter SDK、安装与管理服务仍在 T-03～T-09 中实施。

## 3. 总体架构

### 3.1 三种运行模式

| 模式 | Core | Adapter | Plugin | 使用场景 |
| --- | --- | --- | --- | --- |
| `always_on` | 常驻 | 常驻 | 常驻 | 缺省，行为与 v0.1 相同 |
| `component_idle` | 常驻 | 有条件休眠 | 按需休眠 | 普通 VPS，首要目标 |
| `scale_to_zero` | 可休眠 | 可休眠或由外部接管 | 按需休眠 | 具备外部唤醒的部署 |

`component_idle` 与 `scale_to_zero` 是两级能力：Core 运行期间仍使用插件级休眠。所有自动休眠都可以单独关闭；无法证明某个组件可以安全休眠时保持运行。

### 3.2 责任划分

- **Router** 维护当前有效代次的路由索引。插件进程不存在时，仍知道该插件注册的命令、事件、Service、HTTP 路由与 schedule。
- **Supervisor** 统一执行 EnsureActive、正常停止、并发唤醒合并、进程清理与失败恢复。Router 与 Scheduler 不直接启动 OS 进程。
- **Idle Controller**（Core 内部新模块）根据在途请求、任务状态、后台活动与策略决定是否允许退出，只做决策，不重新实现进程生命周期。
- **Scheduler** 管理触发时间、运行槽、任务身份与结果；插件休眠时仍能触发唤醒。
- **External Wake Provider**（可选）在 Core 已停止或挂起时接收消息、定时触发并唤醒 Core。没有可信的外部唤醒来源时不能进入 `scale_to_zero`。

## 4. 插件级休眠

### 4.1 状态模型

把“是否启用”和“当前是否运行”分开：`enabled` 是配置状态，决定插件能否提供业务；运行状态决定当前是否存在活跃 Session。

| 运行状态 | 含义 |
| --- | --- |
| `STOPPED` | 未运行，或被管理员停用 |
| `WAKING` | 正在启动并等待 ACTIVATED |
| `ACTIVE` | 已就绪，可以处理请求 |
| `QUIESCING` | 不再接纳新请求，准备退出 |
| `SUSPENDED` | 已启用，进程因空闲正常退出 |
| `FAILED` | 启动或运行失败，按恢复策略处理 |

`SUSPENDED` 是管理层新增的正常状态；底层继续复用 `Preparing/Activating/Activated/Stopping/Stopped`。

### 4.2 路由快照

插件的完整路由来自 REGISTER。Core 把**已提交代次的路由描述**单独持久化到状态库：`plugin_id`、`generation_id`、`route_id`，路由类型、匹配条件、优先级、参数与 Schema，HTTP 公共路径、Service 与 schedule 描述，路由内容摘要与安装包摘要。不保存 HTTP 临时 Listener 地址、Session Secret 或进程句柄。

首次激活时验证并保存快照；休眠后唤醒复用当前已提交代次，重新 REGISTER 后校验路由摘要。摘要不一致时停止激活，不悄悄改变业务路由。配置与版本更新仍走 Pending、候选准备与 ActiveGeneration 提交。

### 4.3 唤醒流程

1. Core 收到消息，按路由快照和动态权限完成初步匹配。
2. 目标插件处于 `SUSPENDED` 时，请求进入有界等待队列。
3. Supervisor 为目标插件执行一次 EnsureActive；同一插件的并发唤醒合并为同一次启动。
4. 插件以 `activation_reason=resume` 重新建立 Session，执行正常初始化与注册。
5. Core 确认 ACTIVATED，并验证路由与当前代次一致。
6. Core 再次检查请求截止时间、路由状态与权限，然后交付原始请求。
7. 请求结束后释放活动引用并刷新空闲时间。

不为唤醒新增业务 RPC。请求从进入等待起使用原有的绝对 deadline，冷启动不延长调用时限；取消的请求从尚未交付的队列中移除。已经交付且产生外部副作用的请求维持现有契约：断链不代表撤销，也不自动重新执行。

### 4.4 允许休眠的条件

同时满足：没有在途 Handler、Service、HTTP 或媒体操作；没有运行中的 schedule 回调；没有延续调用或多轮等待；没有需要继续的后台任务或资源租约；没有进行中的升级、配置应用或回退；空闲时间达到阈值；插件声明允许休眠且路由能力满足策略。

Core 无法观察插件自行创建的 goroutine 与外部连接，因此首期只允许 manifest 中声明可休眠、且没有独立后台活动的插件休眠，未声明的保持常驻。确有需求时再提供 SDK 的保持运行租约，不要求插件作者自己管理计时器。

### 4.5 退出与竞争

复用现有 STOPPING：等待请求排空，按停止预算调用 OnStop，关闭 Session、数据库连接与受管资源，确认进程树退出后记 `SUSPENDED`。StopReason 追加 `IDLE`，区分休眠、管理员停用与异常退出。

空闲停止与新请求由同一个生命周期门禁协调：停止尚未开始时可以取消休眠；已经发送 STOPPING 时，新请求等待旧进程退出后再建立新 Session。有限重启规则不变，正常空闲退出不计入异常退出次数。

## 5. Adapter 级休眠（已取消，D-153）

保持 D-26：一个 Adapter 包只有一个进程。同一包下只要有任一实例需要维持接收、发送或重连，进程就不能休眠；可以单独停止某个实例，但这不释放整个进程的内存。

| 场景 | 自动休眠 | 理由 |
| --- | --- | --- |
| Telegram long polling | 常驻 | 停止轮询后无法发现新消息并唤醒自身 |
| Telegram webhook + 外部入口 | 可休眠 | 外部 HTTPS 接收端负责唤醒 |
| OneBot 11 正向 WebSocket | 常驻 | 断开期间缺少可靠的唤醒与补送 |
| OneBot 11 + 可靠外部 Relay | 可休眠 | Relay 持续接收并暂存事件 |
| 只主动发送的 Adapter | 按需唤醒 | 不依赖持续的入站连接 |

v0.1 的 Telegram 只支持 long polling、OneBot 11 只支持正向 WebSocket，不为休眠改变通信模式。S-04 实现 Adapter 的休眠准入与控制，但不让有活跃接收实例的官方 Adapter 默认休眠。

可唤醒的 Adapter 在收到出站调用、外部缓冲事件或管理请求时启动。重新激活时重建连接并验证账号身份，恢复实例配置，重新绑定能力与 extension，恢复 Core 管理的接收游标，连接可用后才交付业务。只有外部明确保证的缓冲与重放能用于可靠恢复，不能因为平台支持重连就假定断线期间的事件会补发。`bot.online`/`bot.offline` 需要区分空闲休眠与真实掉线。

## 6. Core 级与整机休眠（已取消，D-153）

### 6.1 前提

Core 退出后无法自行接收外部请求，也无法靠内部定时器唤醒自己。进入 `scale_to_zero` 必须同时具备：独立于 Core 生命周期的可信唤醒入口；能启动或恢复实例的外部执行者；未交付消息的可靠缓冲与重试；未来定时任务的外部调度；明确的状态持久化与重启恢复。任一条件无法验证时拒绝整机休眠，退回 `component_idle`。

### 6.2 两种后端

- **Process Stop/Start（先支持）**：Core 与子进程正常退出，外部 Supervisor 在需要时重新启动。真正释放 RSS，适用于普通 Linux VPS；代价是重新初始化 Core、Adapter 与插件，外部入口要处理启动窗口。
- **Platform Suspend/Resume（以后可选）**：由支持该能力的托管平台暂停实例，收到请求后恢复。恢复后仍要检查网络连接、时钟变化、认证与任务状态，且不等于普通 VPS 的内存归零。

不用 `SIGSTOP` 模拟休眠：它只停止 CPU 调度，不释放内存。

### 6.3 整机休眠事务

1. Core 确认任务都已结束、没有等待中的调用、没有要求常驻的连接。
2. 确认外部消息入口可以接管。
3. 向外部调度器提交全部未来触发计划，并收到明确的成功确认。
4. 进入 `QUIESCING`，冻结新的根业务请求。
5. 等待现有调用排空，保存必要状态。
6. 外部入口切换到缓冲与唤醒模式并确认成功。
7. Core 停止子进程并退出，或请求平台 Suspend。

任一步失败时恢复正常服务或保持运行，不在未确认外部接管时退出。外部唤醒时，启动者先取得实例的独占启动权（沿用 core.lock 单实例规则），Core 恢复状态并激活必要的 Adapter 与插件，再通知外部入口继续交付。管理 WebUI、HTTP 回调与平台消息经过同一套唤醒安全策略；外部入口必须具备鉴权、限流与防重放。

### 6.4 库模式

库模式的开发组件与 Core 同进程，单独结束 Core 会影响宿主程序。库模式只使用 `always_on` 或子进程级休眠，同进程的开发组件不释放内存。完整 `scale_to_zero` 只面向由外部 Supervisor 管理的独立发行包实例。

## 7. Scheduler 与定时任务

### 7.1 插件级休眠时

1. Scheduler 到达触发时间。
2. 为目标插件执行 EnsureActive，等待 ACTIVATED。
3. 用现有 `scheduled` REQUEST/RESPONSE 调用任务。
4. 记录结果；没有其他工作时插件可以再次休眠。

同一 job 不重叠、不同 job 可并发、任务有独立 deadline 等约束不变。**需要修订的契约**：CONTRACTS §4.3 把 Core 或插件离线期间的 tick 视为跳过。休眠后的 `SUSPENDED` 是可唤醒的启用状态，到期任务照常执行；异常离线仍按原规则跳过。

### 7.2 Core 休眠时的外部调度（已取消，D-153）

每个 job 注册一个一次性的未来触发器（参照 Hermes Chronos）。Core 为每个任务计算下一次 UTC 触发时刻并经 External Wake Provider 注册。例如每天 12:00、16:00、22:00 三个签到任务各有一个触发器，实例只在这三个时刻被唤醒。

到期后：外部定时器唤醒 Core；Core 校验触发凭证与任务身份；持久化认领本次触发；唤醒目标插件并执行；记录结果并计算下一次触发；重新注册触发器；没有其他任务时重新休眠。

### 7.3 时间与去重（整机休眠部分已取消，D-153）

继续使用 `contracts/schedule` 的五字段 cron、IANA 时区与夏令时规则。整机休眠还需要：

- 每次触发有稳定的 `job_id`、计划时刻与调度修订标识。
- 使用计划时刻，不用进程实际醒来的时间冒充计划时间。
- interval 的固定起点持久保存，不在每次唤醒后重新计时。
- 外部触发可以重试唤醒，但已认领的有副作用任务不自动重复执行；持久化认领记录防止同一次触发被并发执行。
- 已开始执行但结果未知的任务记为 `UNKNOWN`，不默默重跑。
- 超时或过期未执行的任务明确记录。

维持“不追补错过的 tick”。允许配置有限的迟到容忍窗口，窗口外记为跳过。语义是至多一次执行尝试，不宣称外部副作用 exactly-once。

### 7.4 调度后端（已取消，D-153）

定义一个小的调度提供者接口，负责提交、取消与核对未来触发计划，不向插件 SDK 暴露具体平台。首批实现：Core 内置 Scheduler（Core 常驻时）与外部 HTTP Wake/Timer Provider（独立进程休眠时）；systemd 或云平台的实现按需增加。不要求自带新的云服务。

## 8. 缺省策略

以下初值在 S-06 按测量调整；可调的值登记到 `internal/tune`（CONTRACTS §16）。

| 参数 | 初值 |
| --- | --- |
| 全局模式 | `always_on`，由管理员开启 |
| 纯命令插件的空闲超时 | 15 分钟；`core_config.json` 的 `sleep.idle_timeout` 可改全局值，`sleep.plugins.<插件 ID>` 可按插件覆盖（D-153） |
| 按插件的休眠策略 | 不设置时按准入规则；`never` 永不休眠；时长为该插件自己的空闲时长；修改立即生效、不重载插件（D-153） |
| 注册了消息类事件路由或 Raw 路由的插件 | 常驻，不建议休眠；管理员显式给出时长后才休眠（D-153） |
| 插件唤醒后最短运行时间 | 5 分钟 |
| 每小时冷启动次数阈值 | 超过 3 次后暂时保持常驻 |
| 有 HTTP、Hook 或持续事件监听的插件 | 常驻 |
| Adapter | 常驻（D-153） |
| Core | 常驻（D-153） |

插件可以声明能够安全休眠，但不能绕过 Core 的停止判定。空闲按实际请求与工作状态统计，不看 CPU 使用率。首期不做自学习策略。

## 9. 接口与持久化

Core 内部接口意图（不是现有 Go 签名）：`EnsureActive(ctx, componentID)` 保证目标就绪并返回活动引用；`ReleaseActivity(...)` 在业务结束时释放引用；`TryIdleStop(componentID)` 检查全部条件，满足时走正常停止；`ReconcileWakeTriggers(...)` 同步外部唤醒计划。

状态库新增：每个组件的有效运行策略与管理状态；每个插件有效代次的路由快照与摘要；Scheduler 的下一次触发计划与认领记录；外部唤醒计划的版本与同步状态；必要的失败计数与诊断。普通请求等待队列属于 Core 的有界运行内存；Core 休眠时未交付的消息由外部入口持久保存。持久化只用现有 SQLite，不引入 Redis。

## 10. 验收要点

验收编号见 TEST-MATRIX V-77～V-81，要点：

- 休眠插件收到首条有效命令后自动激活并执行；100 个并发唤醒只产生一个新 Session。
- 首条请求的权限、原始 Target、Trace、deadline 与顺序约束不丢失。
- 休眠不触发 ActiveGeneration 更新、重新迁移或错误的崩溃恢复。
- 在途的 schedule、Service、HTTP、多轮会话与后台工作阻止休眠；停止过程中到达的请求不造成双进程或错误交付。
- 休眠插件按 12:00、16:00、22:00 等独立计划被唤醒执行；重复的外部触发不造成两次执行尝试。
- Core 休眠前外部消息接管或触发器注册失败时保持运行。
- 未启用休眠时，旧生命周期与事件行为不变。
- 测量冷启动 P50/P95/P99、活跃与休眠时的 PSS/RSS、CPU、唤醒次数、失败与丢弃数。简单 Go echo 插件在固定测试环境中冷启动到 ACTIVATED 的 P95 以 200 ms 为初步目标；其他插件只记录，不统一保证。

## 11. 风险与回退

- **唤醒失败**：请求返回明确错误；有可靠外部缓冲的入口按接纳协议重试，不重复执行结果未知的业务。
- **频繁启停**：最短运行时间与冷启动次数阈值，超出时自动转为常驻。
- **初始化慢**：分别统计 OnStart 与 OnReady 耗时，必要时禁用该插件的自动休眠。
- **连接丢失**：现有长轮询与 WebSocket Adapter 保持常驻，直到有经过验证的外部接收方案。
- **外部调度器故障**：唤醒计划未同步成功时不进入深度休眠；运行中发现故障时继续使用 Core 内置 Scheduler。
- **Core 启动故障**：沿用单实例锁与恢复规则，不建立第二个权威实例，不重新创建空状态库。
- **回退**：管理员把全局模式改回 `always_on` 后，按原有 ActiveGeneration 与配置启动全部已启用组件；不删除路由快照、任务记录与业务数据库。
